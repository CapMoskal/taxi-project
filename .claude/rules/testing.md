# Проверки перед коммитом

Перед любым коммитом обязательны все три, зелёные:

```
npm run build     # tsc -b && vite build — типы + прод-сборка
npm run lint      # oxlint
npm run test:e2e  # @playwright/test — регресс-сеть, ~10с
```

## Регресс-сеть (`e2e/`, `@playwright/test`)

Коммитируемый набор — решение от 2026-07-25, пересматривает более раннее
«не коммитить переиспользуемый раннер» (тогда приложение было скаффолдом,
сейчас выросло достаточно, чтобы ручная перепроверка каждого флоу руками на
каждую сессию не масштабировалась). Подробности решения — `docs/decisions.md`.

- **Цель — `npm run dev`** (`playwright.config.ts`, `webServer`), не
  `preview`/прод: дев-хук `window.__map` (`OrderScreen.tsx`,
  `import.meta.env.DEV`) нужен тестам для проверки геометрии
  маршрута/камеры и существует только в dev. MSW ведёт себя одинаково в
  dev/preview/prod, так что для проверки самого MSW-флоу разницы нет.
- **Внешние API (OSRM, MapTiler) мокаются через MSW**, не через
  `page.route()` — `page.route()` не видит запросы, которые прошли через
  активный Service Worker (проверено эмпирически: запрос виден в
  `page.on('request')`, но обработчик `route()` не срабатывает — fetch
  внутри SW выполняется в отдельном от страницы CDP-таргете). MSW уже и
  есть слой перехвата в этом приложении — мокаем через него же, а не
  вторым несовместимым механизмом. Хендлеры — `src/shared/mocks/e2e-handlers.ts`,
  подключаются в `browser.ts` только когда `VITE_E2E` — переменную
  выставляет исключительно `webServer.env` в `playwright.config.ts`,
  обычный `npm run dev`/прод её не видят, OSRM/MapTiler там как и раньше
  настоящие (см. `.claude/rules/msw-mocking.md`).
- **Наши собственные `/api/*` не мокаются повторно** — это уже MSW
  (`handlers.ts`), е2е-тесты используют тот же мокнутый бэкенд, что и
  обычный dev. Единственная 20%-я случайность (`driver-search` — не
  находит водителя) обрабатывается ретраем в тесте (клик «Повторить
  поиск» в цикле), не мокается отдельно — сценарий retry-UI тоже
  проверяется по пути.
- **Время поездки — `page.clock`**: `driverAssigned→enRoute` (2с) и обе
  6-секундные rAF-анимированные ноги перематываются через
  `page.clock.install()` + `fastForward()` — иначе гейт на каждый коммит
  занимал бы 15+ секунд. Проверено эмпирически: fake clock консистентно
  двигает и `setTimeout`, и `requestAnimationFrame`/`performance.now()`
  вместе. MSW-шные искусственные задержки (`delay()` внутри Service
  Worker) фейком не затрагиваются — остаются короткими честными ждать.
- Запуск: `npm run test:e2e` (headless), `npm run test:e2e:ui` (Playwright
  UI-режим для отладки), `npm run test:e2e:headed` (видимый браузер).
- **Console-ошибки от честно смокированных отказов — не баг, фильтровать
  по URL, не по тексту.** `driver-search` через `SEARCH_FAILURE_RATE=0.2`
  иногда честно отвечает 404 (см. выше) — Chrome логирует ЛЮБОЙ non-2xx
  ответ в консоль как «Failed to load resource» автоматически, даже когда
  приложение обработало это штатно (ретрай). Грабля: у такого
  console-сообщения `msg.text()` — просто общая строка без URL, сам URL —
  только в `msg.location().url`; фильтрация по `.text()` не сработает.
  `full-ride.spec.ts` фильтрует `msg.location().url.includes('/api/driver-search')`
  перед тем как считать ошибку реальной. Полсотни прогонов на этом ловились
  ложные срабатывания, пока не нашли точную причину — см. `decisions.md`.

## CI-бэкстоп (`.github/workflows/ci.yml`)

Автоматический backstop «на всякий случай» (решение Eugene, 2026-07-25) —
не PR-гейт (в проекте нет GitHub PR, фича-ветки живут только локально), а
защита самого `main`: гоняется на каждый пуш в `main` (`build` → `lint` →
`test:e2e`), на случай если кто-то закоммитит без локального прогона. Node
22, `npm install --force` (тот же обход `EBADPLATFORM` от
`@oxlint/binding-darwin-arm64`, что и в `vercel.json` — см. `decisions.md`
2026-07-23), `playwright install --with-deps chromium`. При падении —
`playwright-report` уходит в артефакт GitHub Actions.

## Ad-hoc глубокая проверка (одноразовые скрипты)

Регресс-сеть покрывает ключевые сценарии, но не заменяет разовую глубокую
проверку при отладке нового поведения — для неё по-прежнему `playwright`
(библиотека, не раннер) — devDependency, Chromium скачан
(`npx playwright install chromium`). Одноразовый Node-скрипт через
`require('playwright')` — когда нужно что-то специфичное, чего нет в
закреплённых тестах (кастомный `page.evaluate`, разовая проверка нового
бага). Ничего не коммитить — одноразовые скрипты в scratchpad.

**Playwright MCP — осознанно отложенный пункт** (обсуждали 2026-07-25,
см. `docs/decisions.md` и `docs/roadmap.md`): дал бы быстрый интерактивный
осмотр в диалоге без написания скрипта, но не заменяет ни регресс-сеть,
ни глубокие ad-hoc проверки — вернуться отдельным пунктом, когда
понадобится ускорить именно живое тыканье.

Для фич с реальным UI-поведением — прогонять глазами через dev-сервер
(`npm run dev`), мобильный вьюпорт в первую очередь (mobile-first). **Но с
2026-07-27 в проекте есть десктоп-адаптив** (брейкпоинт `lg` 1024px, эпик
2a/2b/2c в `docs/roadmap.md`) — фичи, которые задевают десктоп-вёрстку,
проверять глазами в ОБОИХ вьюпортах (мобильный + десктоп ≥1024px), не
только в мобильном. Не полагаться только на typecheck/регресс-тесты как на
единственное доказательство того, что фича работает — регресс-сеть
покрывает то, что явно решили закрепить, не всё подряд.

Обязательно проверять `page.on('console', ...)` на ошибки (и в
регресс-тестах, и в ad-hoc скриптах) — экран может отрендериться визуально
нормально, а под капотом падать запрос/редьюсер.
