# ADR-лог — архив: скаффолд-этап (2026-07-13)

Записи ниже перенесены из `docs/decisions.md` при оптимизации 2026-07-20 —
проект дошёл почти до конца роадмапа, эти решения окончательно устоялись
(инструментарий, стартовый выбор карты/токенов/охвата) и с высокой
вероятностью не понадобятся при дальнейшей работе над фичами. Если что-то
из этого всё же всплывёт — здесь полная история со всеми деталями.

---

## 2026-07-13 — MapLibre GL вместо Yandex Maps JS API

Карта — MapLibre GL + бесплатные векторные тайлы (MapTiler free / свой style.json).

**Почему:** полный контроль над видом карты без возни с брендингом/условиями
использования Yandex. Юридический флажок: бесплатная оферта Yandex Maps запрещает
строить конкурирующий картографический сервис и требует не скрывать брендинг —
не критично для такси-флоу, но раз демо кому-то показывают/продают, лучше не
подставлять заказчика. Если когда-нибудь понадобится узнаваемость Yandex-карт —
можно вернуться и свериться с офертой перед продакшеном.

## 2026-07-13 — Фейковая интерполяция маркера вместо routing API

Движение машины по карте — заранее заданный полилайн + интерполяция маркера через
`requestAnimationFrame`, а не реальный routing-сервис (OSRM и т.п.).

**Почему:** это витрина, не работающий бэкенд-продукт. Интерполяция дешевле по
интеграции, не тянет внешнюю зависимость/лимиты и смотрится как живой трекинг —
для демо этого достаточно.

## 2026-07-13 — Широкий охват экранов, не один вылизанный флоу

Делаем профиль, историю поездок, несколько классов такси, экран водителя в пути —
а не один глубоко отполированный флоу заказа.

**Почему:** аудитория показа — сам заказчик (Миша), который будет донастраивать
продукт дальше сам, не разовый питч под конкретного внешнего зрителя. Широкий
охват даёт больше поверхности для его правок и итераций.

## 2026-07-13 — Vite 6 вместо Vite 8 (rolldown-vite) из коробки create-vite

`npm create vite@latest` на момент скаффолда поставил Vite 8 с experimental
rolldown-бандлером — его нативный биндинг (`rolldown-binding.darwin-universal.node`)
не устанавливался из-за рассинхрона версии Node (`22.2.0` vs требуемых
`^20.19.0 || >=22.12.0`), из-за чего `vite build` падал с `MODULE_NOT_FOUND`.

**Почему откатились:** для клиентской витрины важнее предсказуемость тулинга, чем
самая свежая версия. Даунгрейд на `vite@^6` + `@vitejs/plugin-react@^4` убрал
зависимость от нативного rolldown-биндинга — сборка стабильна на текущей версии
Node без обновления окружения. TypeScript оставили на `~5.8` (чистый JS-пакет,
без бинарной зависимости) — нужен был ради `erasableSyntaxOnly` в tsconfig
шаблона.

**Если проблема с Node engine решится (upgrade до Node 22.12+) — можно пересмотреть
переход на Vite 8, не раньше отдельного запроса.**

## 2026-07-13 — `@oxlint/binding-darwin-arm64` явным devDependency

По той же причине (Node `22.2.0` < требуемых `oxlint` версий), npm молча
пропускал установку platform-specific нативного биндинга oxlint из
`optionalDependencies` — `npm run lint` падал с `MODULE_NOT_FOUND`. Добавили
`@oxlint/binding-darwin-arm64` явным `devDependency` — с ним биндинг ставится
детерминированно при любом `npm install`, чистый `rm -rf node_modules &&
npm install` подтверждён рабочим.

**Плата:** явная привязка к платформе (macOS arm64). Eugene работает только на
macOS (см. START_HERE) — приемлемо. Если появится Linux CI/другой арч —
добавить соответствующий `@oxlint/binding-*` или обновить Node до
`>=22.12`/`^20.19`, тогда optional-резолв заработает сам и явную запись можно
будет убрать.

## 2026-07-13 — Playwright как devDependency вместо `chromium-cli`

START_HERE рекомендовал «Playwright CLI как skill» (`chromium-cli`) — лёгкий
браузерный драйвер без постоянного MCP-сервера в контексте. На этой машине
`chromium-cli` не установлен и не является npm-пакетом — недоступен.

**Решение:** `playwright` — devDependency проекта, `npx playwright install
chromium` скачал браузер локально (`~/Library/Caches/ms-playwright`). Никакого
MCP-сервера не подключали — проверка UI идёт через одноразовые Node-скрипты
(`require('playwright')`) по запросу, без постоянного расхода контекста между
задачами. Тот же эффект, что и `chromium-cli`, другим способом.

Context7 MCP подключили как обычно (`claude mcp add`, project scope,
`.mcp.json` в репо) — он и должен быть MCP, задача — свежая документация в
промпт, не браузер.

## 2026-07-13 — Первая фича: XState-машина заказа + пустой экран карты

Реализовано в этом порядке, а не «токены → машина → карта», как изначально
согласовали с Eugene — упустил это при переходе в plan mode, план и апрув
получились сразу на машину+карту. Токены — следующий пункт `docs/roadmap.md`,
ничего не потеряно, но фиксирую расхождение с изначальным порядком честно.

- **`completed` — parallel state** (`payment`/`rating`, независимые final
  под-регионы, `onDone → done`), не плоская последовательность. Так поездка
  может «оплатиться» отдельно от «оценки» — ближе к реальному продукту
  (автосписание карты не обязано ждать оценки пользователя).
- **`done` — не top-level `final`**: настоящий top-level final останавливает
  actor необратимо, что ломает «оформить новый заказ» без ремаунта всего
  провайдера. Вместо этого `done` — обычное состояние с `RESET → idle`.
- **Провайдер (`createActorContext`) скопирован на `OrderScreen`**, не на
  корень `App` — нет причин держать actor живым для будущих экранов
  профиля/истории, которые появятся позже (roadmap п.7-8) без своего роутера.
  *(Уточнение задним числом: провайдер позже, при появлении навигации,
  переехал в `App` — см. запись про навигацию в основном `decisions.md`.)*
- **Без `react-map-gl`** — свой тонкий wrapper `shared/map/MapCanvas.tsx`
  напрямую над `maplibregl.Map` (imperative mount/unmount в `useEffect`).
  На этом шаге ровно один статичный instance карты, ни одного реактивного
  маркера/слоя — декларативная библиотека добавила бы зависимость и ceremony
  без пользы. Пересмотреть, если понадобится много одновременных реактивных
  маркеров/слоёв, управляемых Redux/XState-стейтом.
- **Dev-only debug-панель** (`OrderFlowDebugPanel`, гейт
  `import.meta.env.DEV`, тот же паттерн, что уже в `main.tsx` для MSW) —
  временный UI, чтобы прогонять машину по состояниям без реального
  bottom-sheet/class-picker/driver-card. Будет вырезан по мере появления
  настоящего UI в следующих пунктах roadmap. *(Сделано — панель полностью
  удалена, см. запись про навигацию в основном `decisions.md`.)*
- **Роутер не ставили** — весь текущий и ближайший roadmap (пункты 2-6) это
  один экран заказа, эволюционирующий на месте; роутер понадобится только для
  профиля/истории. *(Уточнение: когда дошли до профиля/истории, роутер всё
  равно не понадобился — завели лёгкий контекст вместо него, см. основной
  `decisions.md`.)*
- **`store.ts` оставили пустым** (`configureStore({ reducer: {} })`) —
  консольный warning от пустого `combineReducers` не фиксили искусственным
  reducer'ом. XState — источник истины для флоу, RTK Query — для серверных
  данных (появится в roadmap п.3-4 вместе с первым реальным api-slice, тогда
  warning уйдёт сам).

## 2026-07-13 — components.json / tsconfig: `paths` продублирован в корневом tsconfig.json

CLI `shadcn` при первом запуске писал файлы в буквальную папку `@/...` в корне
проекта вместо резолва алиаса в `src/`. Причина — root `tsconfig.json` (в
project-references сетапе Vite-шаблона) не содержал `compilerOptions.paths`,
только `references` на `tsconfig.app.json`; shadcn CLI, судя по поведению, не
следует `references` при резолве алиасов.

**Почему решили так:** продублировали `"@/*": ["./src/*"]` и `baseUrl` в
`tsconfig.json` в дополнение к `tsconfig.app.json`. Избыточно, но безопасно —
корневой конфиг всё равно ничего не компилирует (`"files": []`), только отдаёт
метаданные внешним тулам.

## 2026-07-13 — Дизайн-токены: изумрудный `--primary`, скругления и шрифт без изменений

Согласовано с Eugene: акцент — изумрудно-зелёный, скругления — мягкие (дефолт
shadcn не менялся, `--radius: 0.625rem`), шрифт — Geist (уже был).

- **`--primary`, не `--accent`.** Продуктовый акцентный цвет завели через
  `--primary` (уже используется дефолтным вариантом `Button`), а не через
  токен `--accent` — тот в shadcn зарезервирован под нейтральные
  hover/highlight-фоны (dropdown-пункты и т.п.); перекрасить его в зелёный
  означало бы покрасить и все служебные hover-состояния. Подробности и точные
  значения — `.claude/rules/design-tokens.md`.
- **Разная яркость акцента в темах**: `emerald-600` (`oklch(0.596 0.145
  163.225)`) на светлом фоне, `emerald-500` (`oklch(0.696 0.17 162.48)`) на
  тёмном — на тёмном фоне более тёмный оттенок «тухнет» и теряет контраст.
  `--primary-foreground` соответственно инвертирован (почти белый на светлой
  теме, почти чёрный на тёмной) для читаемости текста на кнопках.
- Заодно поправили `--sidebar-primary` в тёмной теме — в дефолтном preset
  shadcn там был случайный синий (`oklch(0.488 0.243 264.376)`), никак не
  связанный с остальной палитрой; привели к тому же изумрудному.
- Проверено визуально через Playwright (light/dark, computed `--primary`/
  `--ring` + скриншот кнопки) — контраст текста на кнопке в обеих темах
  нормальный.
