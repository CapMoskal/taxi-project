## 2026-07-23 — Камера следит за поездкой (throttled follow + override/автовозврат)

Референс — Яндекс.Такси: карта «следит» за поездкой, приближаясь по мере
подъезда, и не борется с пользователем, если он сам подвинул карту. Раньше
`MapCanvas` фитил `routeBounds` **один раз на ногу** (вся геометрия отрезка
целиком) — не следил за движением, не приближался, и на `selectingClass`
камера вообще не двигалась (A+Б не фитились).

- **Камера вынесена из `MapCanvas` в отдельный хук `useMapCameraFollow`**,
  вызывается из `OrderScreen`. `MapCanvas` перестал знать про `routeBounds`
  — единый источник управления камерой, не два конкурирующих (был бы риск,
  что `MapCanvas`'ный fit и хук дерутся). Throttled `fitBounds` (~раз в
  секунду, не на каждый rAF-кадр) — на статичном [A,Б] один фит, в
  движении переодически поджимает кадр по мере сближения точек (создаёт
  эффект приближения «на весь экран», без явного ручного управления zoom).
- **Кадр — «такси + следующая точка», не «такси + Б всегда»**: на
  `enRoute` — такси+A (куда машина реально едет), на `inRide` — такси+Б.
  Согласовано с Eugene явно (буквальная формулировка «такси+Б» была
  рассмотрена и отклонена — не показывает актуальную цель движения).
- **Override без кнопки recenter** — согласовано явно с Eugene. Только
  автовозврат по таймеру (4с бездействия). Гейт на `dragstart`/`zoomstart`/
  `rotatestart` через `e.originalEvent` — отличает жест пользователя от
  программного `fitBounds` (у которого `originalEvent` нет).
- **Реальный баг, найденный и исправленный при проверке (не гипотетический —
  подтверждён Playwright'ом с настоящим mouse-drag):** гейт на `originalEvent`
  ошибочно стоял и на `moveend` (по аналогии с `dragstart`). Оказалось,
  MapLibre после отпускания пальца/мыши применяет **инерционное
  доторможение** (`DragPanHandler`, инерция по накопленной скорости за
  последние ~160мс движения) — финальный `moveend`, которым это
  доторможение завершается, диспатчится **программно, без `originalEvent`**.
  С гейтом на `moveend` таймер автовозврата попросту никогда не
  планировался при быстром (флик-style) драге — слежение зависало в
  suppressed навсегда. Исправление: гейт на `moveend` убран, оставлена
  только проверка `suppressedRef` (сам флаг ставится только настоящим
  жестом через `dragstart`/`zoomstart`, так что момент включения
  по-прежнему защищён от программных фитов — только момент выключения не
  должен требовать `originalEvent`).
- **Тот же баг был и в уже смёрженном `DestinationSheet`** (фича bottom
  sheet, предыдущий пункт) — retreat-восстановление плашки после
  взаимодействия с картой гейтилось на `originalEvent` в `moveend` точно
  так же и так же ломалось бы на быстром флик-драге карты (плашка
  оставалась бы `retreated` навсегда). Пофикшено тем же способом в этом же
  коммите, а не отдельным — найдено по прямой аналогии при написании этой
  фичи, не отдельная сессия отладки.
- **Дев-хук `window.__map`** (`OrderScreen.tsx`, гейт `import.meta.env.DEV`):
  для Playwright-проверки камеры — чтение `map.getCenter()`/`getZoom()`
  напрямую надёжнее, чем реконструировать состояние камеры по экранным
  позициям маркеров (шумно — маркер такси сам двигается по ходу поездки,
  что маскирует, следит камера или нет). Не попадает в прод-сборку.
- **Padding по фазе**: `selectingClass`/`searchingDriver` (нижний шит) —
  больше `bottom`; `driverAssigned`/`enRoute`/`arrived`/`inRide`
  (`DriverCard` сверху) — больше `top`.
- Проверено (Playwright, реальная сеть OSRM): [A,Б] в кадре на
  `selectingClass`; слежение в движении — driver-маркер заметно двигается
  между сэмплами, кадр пересчитывается; ручной drag во время `inRide` не
  вызывает мгновенный snap-back (камера не борется с жестом); override +
  автовозврат подтверждён на статичной фазе (`selectingClass`) через
  polling `window.__map.getCenter()` — после драга камера смещается,
  держится смещённой ~1.5с, затем сама возвращается к исходному
  auto-fit-центру. Ноль консольных ошибок на всех прогонах.

- **2026-07-23 — Два бага пост-мёржа `camera-follow` (по скринам Eugene),
  оба в `DestinationSheet.tsx`:**
  1. **Прямая линия маршрута сразу после подтверждения Б.** Причина: до
     фикса `useGetRouteQuery({from: pickup, to: destination})` стартовал
     только в `OrderScreen`/`useRideAutomation` **после** `CONFIRM_DESTINATION`
     — реальный запрос к OSRM (не мок, задержка сети непредсказуема) ещё в
     полёте, пока рендерится `selectingClass`, `roadOrStraight` честно падает
     на прямую до ответа. Раньше это маскировалось (быстрый локальный OSRM
     при разработке), на реальной сети — заметная прямая линия. **Фикс**:
     прогрев кэша RTK Query — тот же `useGetRouteQuery` подписан ещё внутри
     `DestinationSheet`, пока плашка открыта, на `{from: pickup, to:
     candidateDestination}` (`candidateDestination` = то, что прочитает
     `handleConfirm`, обновляется на каждый `moveend`, включая программный
     `jumpTo` от выбора адреса — без гейта на `retreated`, в отличие от
     `draggedCenter`). Один и тот же сериализованный ключ аргументов → к
     моменту тапа «Подтвердить» запрос уже разрешён (или почти), `OrderScreen`
     переиспользует кэш вместо нового фетча. Проверено Playwright: список
     реальных запросов к `router.project-osrm.org` не содержит повторного
     запроса для пары pickup→destination после подтверждения — только тот,
     что стартовал во время открытой плашки; `route-line`-источник карты
     сразу после подтверждения содержит road-геометрию (десятки точек), не
     двухточечный fallback.
  2. **Кнопка «Подтвердить точку назначения» не видна без разворота
     плашки.** Причина: кнопка была последним ребёнком внутри свайпаемого
     `motion.div` (`h-[70vh]`, `translateY` по снапу). В дефолтном `peek`
     (`y = sheetHeight * 0.62`) видны только верхние ~38% плашки (шапка +
     инпут) — весь низ, включая кнопку, уезжал за нижний край экрана вместе
     с `translateY`. Не баг «в expanded списком перекрывает» — баг в том,
     что кнопка физически была частью уезжающего контента. **Фикс**:
     кнопка вынесена в отдельный `<div>`-сиблинг вне `motion.div`, `z-30`
     (плашка — `z-20`), `absolute inset-x-0 bottom-0` — не участвует в
     translateY снапа, видна всегда (`peek`/`expanded`/`retreated`).
     Список получил `pb-20`, чтобы последняя строка не пряталась под
     постоянным футером. Проверено Playwright: `boundingBox()` кнопки
     полностью внутри вьюпорта в дефолтном `peek`-состоянии без единого
     жеста.
  - Оба фикса — точечные, без нового пункта роадмапа (не архитектурная
    фича), по прямому запросу Eugene после ручной проверки на реальном
    устройстве/скринах.

- **2026-07-23 — Убрать «Начать заказ», `selectingPickup` = интерактивный
  первый экран (полная модель Яндекса, референс-скрин от Eugene):**
  - **Машина**: `initial: 'idle'` → `initial: 'selectingPickup'`, состояние
    `idle` и событие `START_ORDER` удалены целиком. `CANCEL_RIDE`/`RESET`
    ретаргетнуты с `idle` на `selectingPickup` — `resetOrder` очищает
    `pickup`, `PickupResolver` (гейт `pickup === null`) на новый заказ
    сеет геолокацию заново, поведение то же, что раньше давал `idle`.
  - **Развилка «сколько экранов»** — решили с Eugene: **два шага**, не
    один. `selectingPickup` — свой экран (двигаешь A, потом жмёшь «Куда
    едем?»), `selectingDestination` — отдельный (текущий
    `DestinationSheet`, не тронут функционально). Не стали схлопывать в
    один экран с сразу двумя точками — это отдельная, более крупная
    переделка `DestinationSheet`, не входила в запрос.
  - **`PickupResolver.tsx`** разделён на два: сам `PickupResolver` стал
    headless-сидером геолокации (убран авто-`CONFIRM_PICKUP` — раньше он
    проскакивал `selectingPickup` сразу же, что было ровно тем поведением,
    которое теперь отменяем), весь UI выехал в новый `PickupSheet.tsx`.
  - **`PickupSheet.tsx`**: центр-пин = точка A, `moveend` → `SET_PICKUP` —
    тот же паттерн, что `DestinationSheet` уже использует для Б. Два бага
    найдены и пофикшены в процессе (Playwright, реальная геолокация):
    1. **Список без капа по высоте закрывал центр-пин.** `BottomSheet` без
       ограничения высоты растягивался под 5 моковых недавних адресов
       почти до середины экрана — центр-пин (= истинный `map.getCenter()`,
       та же координата, что уйдёт в `pickup`) визуально прятался под
       шитом, хотя технически всё работало верно (WYSIWYG ломался только
       зрительно). Фикс: `max-h-[45vh] flex flex-col` на `BottomSheet` +
       `min-h-0 flex-1 overflow-y-auto` на список (тот же приём, что
       `DestinationSheet.tsx` уже использует для своего списка).
    2. **`jumpTo` при выборе недавнего адреса корраптил `pickup`.**

       шлёт `CONFIRM_PICKUP` — но `moveend`-listener (ещё смонтирован в
       момент вызова `jumpTo`, React не размонтировал `PickupSheet`
       синхронно) принимал этот программный прыжок за «пользователь
       подвинул A» и переписывал `pickup` координатами Б через
       `SET_PICKUP`. Итог — `pickup === destination`, OSRM на

       `e.originalEvent` (как в `DestinationSheet`/`useMapCameraFollow`) —
       здесь после `jumpTo` НЕ нужно вообще никакой реакции на `moveend`

  - **Тап по недавнему адресу на `selectingPickup`** ведёт на
    `selectingDestination` с центр-пином Б уже на этом адресе (не сразу в

    OSRM, MapTiler): загрузка без «Начать заказ» → сразу интерактивный

- **2026-07-23 — Демо для Миши: хостинг на Vercel + MSW включается и в
  prod.** Обсуждали два пути показать демо: локальный запуск у Миши
  (`npm run dev`/`preview`) vs хостинг. Eugene выбрал хостинг — ключевая
  причина: Миша должен видеть **последующие** правки по мере того, как мы
  их вносим, без ручной синхронизации/перезапуска на его стороне. Vercel
  (а не Netlify/GH Pages) — не принципиально, но: zero-config для Vite,
  автодеплой на каждый пуш в GitHub `main` закрывает «видит новые правки»
  само по себе, https из коробки (нужен геолокации — secure context), и
  никакого гемора с sub-path/service-worker scope, который был бы на
  GitHub Pages (прод-сборка там на `/repo-name/`, а не в корне).
  **Разобранный нюанс, который чуть не завёл не туда:** MSW — единственный
  «бэкенд» проекта, но исторически гейтился на `import.meta.env.PROD`
  (см. `.claude/rules/msw-mocking.md`, на момент этой записи ещё не
  обновлён) — значит обычная прод-сборка (то, что уедет на любой
  хостинг) отдаёт красивую оболочку с полностью мёртвыми запросами.
  Разбирали три варианта: (а) хостить `dev` — не для этого предназначен,
  не вариант для публичного хостинга; (б) хостить `preview` — не решает
  проблему, `vite preview` раздаёт ТУ ЖЕ прод-сборку, MSW там тоже
  выключен; (в) снять `PROD`-гейт, MSW работает и в prod. Выбрали (в) —
  единственный вариант, при котором задеплоенная сборка работает
  полностью, как и было задумано изначально («нет бэкенда = MSW
  имитирует», см. `CLAUDE.md`) — просто теперь это верно в любой среде,
  не только в dev. **Дальше по плану** (см. `roadmap.md`): снять гейт в
  `main.tsx`, обновить `.claude/rules/msw-mocking.md` (сейчас там написано
  «MSW включается только в dev» — как только гейт снят, это устареет, не
  забыть поправить в этом же коммите/фиче, не оставлять расхождение
  между кодом и правилами), завести проект на Vercel с автодеплоем
  `main`, проверить PWA-установку и геолокацию с реального телефона.

- **2026-07-23 — Реализация деплой-фичи: MSW-first, Workbox-SW не
  регистрируется.** По ходу реализации всплыла развилка, которой не было
  в обсуждении выше: **MSW и Workbox-PWA-SW не могут работать вместе** —
  оба претендуют на scope `/`, страницу контролирует только один service
  worker. До сих пор они не пересекались случайно (MSW — только dev,
  PWA-SW — только прод); сняв гейт, мы столкнули их лбами. Решение
  Eugene: **MSW важнее** (рабочие данные — суть демо), Workbox-SW — в
  жертву. Реализация:
  - `main.tsx`: гейт `if (import.meta.env.PROD) return` удалён — MSW
    стартует всегда (dynamic import остался, `bypass` остался).
  - `vite.config.ts`: `injectRegister: false` — Workbox-SW и манифест
    по-прежнему собираются, но регистрация SW в приложение не инжектится
    (`registerSW.js` больше не генерится, `sw.js` лежит в `dist/`
    инертным). Манифест-линк и `theme-color` в `index.html` остаются —
    установка «на экран Домой» работает. Потеряли: precache оболочки и
    офлайн-кэш тайлов MapTiler. `OfflineBanner` жив (он от
    `navigator.onLine`, не от SW). Если появится реальный бэкенд — просто
    вернуть `injectRegister`.
  - `vercel.json`: SPA-rewrite `/(.*)` → `/index.html` (реальные файлы
    Vercel отдаёт напрямую, rewrite ловит только несуществующие пути).
  - Ручные шаги на стороне Eugene (не автоматизируемы — его аккаунты):
    импорт репо в Vercel + env-переменная `VITE_MAPTILER_KEY` (ключ
    гитигнорится в `.env`, без него карта не загрузится) + проверка с
    реального телефона.
  - Проверено локально (Playwright на `npm run preview` — та же
    прод-сборка, что уедет на Vercel; свежий браузер-контекст, чтобы
    старый Workbox-SW с прошлых локальных preview не влиял): MSW
    перехватывает `/api/*` (профиль «Евгений», классы с ценами, недавние
    адреса — всё рендерится, в консоли `[MSW] 200 OK`);
    `navigator.serviceWorker.getRegistrations()` → ровно одна
    регистрация, `mockServiceWorker.js` на scope `/`; сквозной путь
    А → Б → классы с road-маршрутом; ноль ошибок в консоли.
  - **Грабля на первом же деплое: `EBADPLATFORM`.** Установка зависимостей
    на Vercel (Linux x64) падала из-за `@oxlint/binding-darwin-arm64` —
    явного macOS-arm64 devDependency, добавленного 2026-07-13 как
    осознанный костыль под локальный Node 22.2.0 (см.
    `_archive/decisions-scaffold.md` — там же было предсказано, что при
    появлении Linux-окружения запись придётся пересматривать). Прямой dep
    под чужую платформу — жёсткий фейл npm; убрать нельзя (локальный lint
    ломается — проверено на свежем клоне), в `optionalDependencies`
    нельзя (npm молча пропускает его из-за того же engine-mismatch — тоже
    проверено, исходная проблема костыля). Решение:
    `"installCommand": "npm install --force"` в `vercel.json` — `--force`
    обходит платформенную проверку (проверено зеркальным экспериментом:
    linux-биндинг на macOS с `--force` ставится, lint работает); oxlint
    на Vercel всё равно не запускается (build = `tsc -b && vite build`).
    Чистое снятие костыля = обновить локальный Node до `>=22.12` — тогда
    и явный биндинг, и `--force` можно убрать (отдельной задачей).

- **2026-07-25 — Коммитируемая регресс-сеть на `@playwright/test`,
  пересмотр решения от 2026-07-13.** Изначально (`_archive/decisions-scaffold.md`,
  2026-07-13) решили НЕ коммитить переиспользуемый Playwright-раннер —
  тогда приложение было скаффолдом, разовых Node-скриптов хватало. К
  2026-07-25 приложение выросло настолько, что ручная перепроверка всех
  флоу руками в каждой сессии перестала масштабироваться — Eugene
  запросил регресс-сеть явно, обсудив альтернативы (см. ниже «отложенный
  пункт»). Развилки, решённые с Eugene:
  - **Гонять `npm run test:e2e` перед КАЖДЫМ коммитом**, наравне с
    build+lint (не только перед мёржем) — обязывает набор быть быстрым
    и детерминированным.
  - **Внешние API (OSRM, MapTiler) мокаются**, не реальная сеть — ради
    скорости/стабильности гейта-на-коммит; реальную интеграцию по-прежнему
    проверяем ручным прогоном по живому URL (как и раньше).
  - Мои технические решения (обоснованы фактами, не форки с Eugene):
    - **Цель тестов — `npm run dev`, не `preview`.** MSW одинаково себя
      ведёт в dev/preview/prod (см. запись выше про Vercel), но дев-хук
      `window.__map` (`OrderScreen.tsx`) существует только при
      `import.meta.env.DEV` — тестам он нужен для проверки геометрии
      маршрута и камеры.
    - **Внешние API мокаются через MSW, не `page.route()`.** Первая
      попытка — мокать OSRM/MapTiler через `page.route()` в тестовом
      файле — не сработала: запросы были видны в `page.on('request')`,
      но обработчик `route()` ни разу не сработал. Причина — активный
      Service Worker (MSW): fetch, который SW пропускает дальше в сеть
      (`onUnhandledRequest: 'bypass'`), выполняется в собственном
      контексте SW, отдельном CDP-таргете от страницы — `page.route()`
      этого не видит (подтверждено экспериментом: добавил
      `console.log` в обработчик route — ни разу не вызвался, при этом
      сами запросы шли и долетали до реального OSRM/MapTiler). Раз MSW
      и так уже единственный слой перехвата в приложении — мокаем через
      него же: `src/shared/mocks/e2e-handlers.ts` с хендлерами для OSRM/
      MapTiler (geocoding + style), подключаются в `browser.ts` только
      когда `import.meta.env.VITE_E2E` — переменную выставляет
      исключительно `webServer.env` в `playwright.config.ts`; обычный
      `npm run dev` и прод (Vercel) её не видят, там OSRM/MapTiler
      остаются настоящими сервисами, как и задумано изначально. Мок-стиль
      карты — `{version:8, sources:{}, layers:[]}` (валидный, карта
      грузится мгновенно офлайн; MapLibre не запрашивает тайлы для
      несуществующих источников — отдельно мокать тайлы не пришлось).
    - **Собственные `/api/*` не мокаются повторно** — тесты используют
      тот же MSW-бэкенд, что и обычная разработка. `driver-search` имеет
      встроенную 20%-ю случайность отказа (`entities/driver/mocks.ts`) —
      обрабатывается ретраем в самом тесте (клик «Повторить поиск» в
      цикле до появления `DriverCard`), не отдельным мокoм — заодно
      покрывает retry-UI.
    - **`page.clock` для перемотки времени поездки.** Полный флоу
      завязан на реальные задержки: `driverAssigned→enRoute` (2с,
      `setTimeout` в `useRideAutomation.ts`) и две 6-секундные rAF-
      анимированные ноги (`useAnimatedPosition.ts`, время читается через
      `performance.now()`). Без перемотки — 15+ реальных секунд на
      каждый прогон, неприемлемо для гейта-на-коммит.
      `page.clock.install()` + `fastForward()` эмпирически подтверждён
      консистентно двигающим и `setTimeout`, и rAF/`performance.now()`
      вместе (мини-эксперимент до написания финального теста: статус
      карточки водителя корректно переходил «Едет к вам» →
      «Ждёт у подъезда» после одного `fastForward(6200)`). MSW-шные
      искусственные задержки (`delay()` внутри Service Worker) фейком не
      затрагиваются — не тот JS-контекст — остаются короткими честными
      ожиданиями (~0.5–2.5с), это и ограничивает нижнюю границу времени
      прогона (не 15с, но и не мгновенно).
  - **Санити-проверка**: временно сломал `roadOrStraight()` (вернуть
    всегда прямую линию) — тест `pickup-destination.spec.ts` покраснел
    ровно на той самой проверке, что и должен (`coords.length > 2`);
    откатил. Подтверждает, что набор реально ловит регресс, а не просто
    зелёный по случайности.
  - Набор: `e2e/smoke.spec.ts`, `e2e/pickup-destination.spec.ts`,
    `e2e/full-ride.spec.ts` (полный happy-path A→оплата/рейтинг→RESET).
    Весь прогон — секунды (~10с локально), не десятки.
  - **Флейк в `full-ride.spec.ts`, найден и пофикшен в тот же день.**
    После первого коммита набора Eugene попросил ещё и CI-бэкстоп (ниже) —
    при проверке в чистом окружении (свежий `git clone`-эквивалент,
    `npm install --force`, без прогретого `node_modules/.vite`)
    `full-ride.spec.ts` иногда падал на `expect(errors).toEqual([])`.
    **Первая гипотеза оказалась неверной**: заподозрил гонку параллельных
    воркеров с холодным кэшем Vite (по 4 браузера одновременно бьют в
    только что стартовавший dev-сервер) — временно поставил `workers: 1`
    для CI. Прогнал 12 раз подряд локально с `--workers=1` — всё зелёное,
    гипотеза выглядела подтверждённой. Но при повторной проверке уже
    ОБЫЧНОГО (не чистого) окружения тест всё равно иногда падал даже в
    одиночном прогоне без параллелизма — гипотеза не выдержала. Добавил
    прицельное логирование (`page.on('response')`/`page.on('requestfailed')`)
    и погонял ~12 раз — поймал настоящую причину: `entities/driver/mocks.ts`
    имеет честную `SEARCH_FAILURE_RATE=0.2` на `/api/driver-search` — при
    срабатывании MSW отвечает 404 (это штатное поведение мока, тест уже
    обрабатывает это ретраем «Повторить поиск»), но Chrome ЛЮБОЙ non-2xx
    ответ логирует в консоль как «Failed to load resource» автоматически,
    независимо от того, обработало ли приложение это штатно. `errors`-массив
    в тесте ловил и это тоже. Убрал спекулятивный `workers: 1` (не был
    реальной причиной), пофиксил по существу: `full-ride.spec.ts`
    фильтрует такие сообщения по `msg.location().url.includes('/api/driver-search')`
    — **не по `msg.text()`**, там просто общая строка без URL, ловушка на
    будущее для похожих фильтров. Подтверждено статистически: 22 подряд
    зелёных прогона после фикса (шанс так повезти при живом баге с 20%-й
    частотой — около 0.5%).
  - **CI-бэкстоп** (`.github/workflows/ci.yml`, запрошено Eugene «на

## 2026-07-25 — Наполнение профиля: подстраницы по референсу Яндекс.Такси (не клон)

Миша попросил больше «наполненности» в приложении. Eugene прислал скрин
профиля Яндекс.Такси как референс — обсудили, что из него органично для
витрины такси на этом этапе, а что нет.

- **Взяли:** ряд из 4 иконок-кнопок под аватаром (Заказы/Поддержка/Адреса/
  Настройки — даёт ощущение «дорого» почти бесплатно), полная страница
  «Способы оплаты» (список + честная MSW-мутация «добавить карту»),
  «Адреса» (Дом/Работа), «Настройки» (реальный переключатель темы +
  тумблер уведомлений), «Информация» (статика), «Поддержка» (FAQ-заглушка).
- **Явно НЕ взяли** (обсуждено с Eugene): «Избранное» (пересекается по
  смыслу с «Адресами», дублирование без пользы), «Кешбэк и скидки»/«Сейф»/
  «Помогать с Яндексом» (геймификация конкретно Яндекс.Плюс/эко-проекта —
  проект прямо не клон Яндекса, копировать их фирменную механику
  бессмысленно), «Бизнес-аккаунт»/«Семейный аккаунт» (мультиаккаунтность —
  отдельная модель данных, весь остальной флоу заказа её не поддерживает,
  несоразмерно ради косметики).
- **`paymentMethod` вынесен из `UserProfile` в отдельную entity
  `entities/payment-method/`** — единый источник истины (список карт +
  наличные, одна с `isDefault`). Проверено перед миграцией: поле читалось
  только в `ProfileScreen`, не в шаге оплаты поездки (`RideCompletionSheet`)
  — миграция безопасна для флоу заказа.
- **Новая entity `entities/saved-place/`** (Дом/Работа), отдельно от
  `entities/recent-place/` — разная семантика (помеченные пользователем
  адреса vs авто-собираемые недавние точки), не смешивать в один эндпоинт.
- **«Добавить карту» — честная MSW-мутация**, не заглушка: `POST
  /api/payment-methods` дописывает карту в module-scoped массив внутри
  хендлера, RTK `addCard` с `invalidatesTags` перечитывает список. В духе
  правила проекта «моки имитируют поведение честно», не просто рисуют
  статичный UI.
- **Профильные подстраницы — без рандомной инъекции ошибок.** Правило
  «ошибочные ответы иногда» уже реализовано на `driver-search`
  (единственный намеренный флейк, см. запись выше про регресс-сеть) —
  здесь это была бы просто порча демо без пользы, не стали повторять.
- **Переключатель темы — настоящий, не бутафория.** `.dark`-токены в
  `index.css` были определены с самого начала (design-tokens.md,
  2026-07-13), но ничего в приложении их не включало — тема всегда была
  светлой. Завели `app/ThemeProvider` (состояние `light|dark|system`,
  класс `.dark` на `document.documentElement`, персист в `localStorage`,
  `system` слушает `matchMedia`) — по образцу уже существующего
  `NavigationProvider`. Это UI-состояние приложения, не серверные
  (мокнутые) данные и не флоу заказа — сознательно НЕ через RTK Query и
  не через XState (правило проекта: RTK — источник истины для мокнутых
  данных, XState — для флоу заказа, тема ни то ни другое).
- **Навигация — плоский `Screen`-union расширен на 5 значений**, без
  стека: дерево мелкое (order → profile → подстраница), «назад» у всех
  подстраниц ведёт в profile — тот же паттерн, что уже был у `history`.
  Стек посчитали оверинжинирингом для текущей глубины навигации.
- Заодно вынесен `shared/ui/ScreenHeader` (был продублирован в
  `ProfileScreen`/`RideHistoryScreen`) и добавлены переиспользуемые
  `ListRow`/`Switch` — общие для всех новых подстраниц.
- Регресс-сеть: `e2e/profile.spec.ts` — навигация по всем подстраницам без
  console-ошибок, добавление карты, переключение темы (assert на класс
  `.dark`). При ручной проверке (`npm run dev`, мобильный вьюпорт) нашли и
  сразу поправили мелкий баг форматирования — список карт показывал
  «•• 0542» (2 точки) вместо принятого везде «•••• 0542» (4 точки).
