## 2026-07-15 — Реальный MapTiler style + rAF-интерполяция маркера водителя

Заменили demo-style MapLibre на `basic-v2` от MapTiler (ключ в `.env`,
`VITE_MAPTILER_KEY`, шаблон — `.env.example`). Добавили трекинг маркера
водителя по заранее заданному полилайну через `requestAnimationFrame` (без
routing API — согласуется с более ранним решением про фейковую
интерполяцию).

- **`shared/map` не зависит от `features/order-flow`.** Свой тип `LatLng` в
  `shared/map/types.ts`, структурно идентичный `GeoCoords` — конвертация не
  нужна благодаря структурной типизации TS, но направление зависимости
  архитектурно чистое (`shared` не импортирует из `features`).
- **Синк в XState — throttled (~2/сек), а не на каждый кадр.** Визуальная
  позиция маркера обновляется 60 раз/сек локально (проп в `MapCanvas`), но
  `DRIVER_LOCATION_UPDATE` в actor шлётся не чаще раза в 500мс — иначе на
  каждый rAF-тик перерендерились бы все подписчики `useOrderFlowSelector`.
  Не противоречит правилу CLAUDE.md «XState — источник истины для флоу»: то
  правило про несмешивание с RTK Query (серверными) данными, а не про частоту
  апдейтов внутри одного источника.
- **Маркер и `fitBounds` — обязанность `MapCanvas`.** Компонент сам создаёт/
  двигает/удаляет `maplibregl.Marker` по пропу `markerPosition`, и подгоняет
  камеру под текущий отрезок маршрута по пропу `routeBounds` (стабильная
  ссылка на полилинию — рефит происходит только на смену отрезка, не на
  каждый кадр). Консьюмеры не трогают `maplibregl.Map`/`Marker` напрямую.
- **`fitBounds` — не было в исходном плане, добавили по факту проверки.**
  Первая сборка визуально проверялась только на отрезке `enRoute` (точка
  подачи рядом с центром карты) — на `inRide` пункт назначения (~6.5км)
  уезжал за пределы вьюпорта, маркер пропадал из виду. Это провалило бы
  собственную цель фичи («видно, как едет машина»), поэтому добавили
  `map.fitBounds()` на старте каждого отрезка (`MapCanvas`, проп
  `routeBounds`) сразу, не откладывая на отдельный шаг.
- **Переходы между состояниями машины по-прежнему ручные** (кнопки
  debug-панели) — анимация просто замирает на конечной точке отрезка, если
  пользователь не нажал следующую кнопку. Автозавершение по концу анимации —
  не в этой фиче, пересекается с реалистичными MSW-задержками из следующих
  пунктов roadmap.
- Демо-координаты (`DEMO_PICKUP`/`DEMO_DESTINATION`) переехали из
  `OrderFlowDebugPanel.tsx` в `features/order-flow/demoRoute.ts` — старые были
  ~100м друг от друга (случайно почти совпадали), непригодны для видимого
  маршрута.
- Цвет маркера — `var(--primary)`, резолвится корректно в SVG `fill`
  (MapLibre ставит его через `setAttributeNS`, не инлайн-стиль — CSS custom
  properties тем не менее резолвятся, проверено визуально).

## 2026-07-15 — Класс такси / выбор точки подачи: bottom-sheet, MSW-цены, точки A/B

Первый настоящий UI вместо debug-кнопок для `selectingDestination` и
`selectingClass`: центр-пин + drag карты для точки назначения, bottom-sheet
(Motion) с классами такси и ценой от расстояния A→B через MSW. Заодно —
первый реальный RTK Query api-slice в проекте.

- **`shared/geo/` вынесен из `shared/map`** (`LatLng`, `haversineDistanceMeters`)
  — нужен MSW-хендлеру расчёта цены, а `entities/*`/mock-слой не должны
  зависеть от `shared/map` (это рендеринг карты, не геометрия). `GeoCoords`
  (`features/order-flow`) и `RideClassId` (теперь в `entities/ride-class`) —
  ре-экспорты из канонических мест, чтобы не плодить дублирующиеся типы и не
  тянуть entity→feature зависимость в обратную сторону.
- **`app/store.ts` получил первый реальный reducer** (`rideClassApi`) —
  давний консольный warning про пустой `combineReducers({})` наконец исчез
  (подтверждено в браузере: список ошибок пуст после прогона флоу).
- **Точка назначения подтверждается через `map.getCenter()` в момент клика**,
  не непрерывным отслеживанием центра на каждый пиксель драга — дешевле,
  `MapCanvas` уже отдаёт `maplibregl.Map` через существующий `onMapLoad`.
- **`MapCanvas.markerPosition` обобщён в `markers: MapMarker[]`** (diff по
  `id`) — нужно одновременно показывать пин A, пин B и маркер водителя.
  Добавлены `routeLine` (GeoJSON line-слой) и `showCenterPin` (CSS-оверлей,
  не привязан к гео-координате).
- **Реальный баг, пойманный при проверке в браузере**: `var(--foreground)`
  прекрасно резолвится как SVG `fill` у `maplibregl.Marker` (нативный CSS
  движок браузера), но **не резолвится** в `paint`-свойстве MapLibre-слоя
  (`addLayer`) — это WebGL-рендеринг со своим валидатором цвета, он не знает
  ни про CSS custom properties, ни про `oklch()`. Дальше выяснилось, что
  современный Chrome/`getComputedStyle` тоже не приводит `oklch()` к `rgb()`
  автоматически (сохраняет исходное цветовое пространство) — пришлось
  дополнительно прогонять через 1×1 canvas (`fillStyle` + `getImageData`),
  который гарантированно квантует любой CSS-цвет в sRGB-байты. См.
  `resolveCssColor` в `MapCanvas.tsx`. Ограничение: цвет так «запекается»
  один раз при создании слоя — не переживёт переключение темы налету (сейчас
  тумблера тёмной темы в приложении всё равно нет, не критично).
- **Полилинии водителя (`useDriverLocationSimulator`) стали динамическими** —
  раньше ехали по захардкоженным точкам, теперь строятся из
  `context.pickup`/`context.destination` через `useMemo` (иначе новый array
  literal каждый рендер ломает контракт `useAnimatedPosition` на стабильность
  ссылки). Точка старта водителя (`enRoute`) — не фиксированная точка на
  карте, а смещение относительно pickup (`getDriverStartPoint`), иначе после
  будущей геолокации машина стартовала бы у случайной точки на другом конце
  города.
- **Debug-панель полностью скрыта** (не только кнопки — весь блок) на
  `selectingDestination`/`selectingClass`, чтобы не наслаивалась с новым
  нижним UI в тех же координатах. Остальные состояния — без изменений.
- **Цвета пинов** — без новых токенов: pickup `var(--foreground)` (чёрный,
  «старт»), destination `var(--destructive)` (красный, классический пин
  «финиш»), водитель `var(--primary)` (изумрудный, как раньше).
- Bottom-sheet — простая версия (`motion.div` slide up/down), без
  drag-to-dismiss физики — по явному запросу Eugene, «улучшенная» версия
  отдельно и потом.
- Реальная геолокация пользователя (точка A) — тоже отдельно и потом, сейчас
  фиксированная демо-точка.

## 2026-07-15 — Поиск водителя: недетерминированный MSW-мок + карточка-инициалы

Реальный UI для `searchingDriver` (`entities/driver` + `DriverSearchPanel` +
`DriverCard`), заменяет debug-кнопки `DRIVER_FOUND`/`SEARCH_FAILED` со
статичным водителем.

- **Первый мок в проекте с недетерминированным результатом**: MSW-хендлер
  `GET /api/driver-search` — случайная задержка ~1.5–2.5с, ~20% случаев
  отвечает 404 («поблизости нет свободных водителей»), иначе отдаёт
  случайного водителя из пула на 3 профиля. Раньше (`ride-classes`) моки
  были error-prone только по форме (delay), но всегда 200. Соответствует
  `.claude/rules/msw-mocking.md` — не только happy path.
- **Ретрай — через `refetch()` RTK Query**, не через новый state в машине:
  `useSearchDriverQuery` уже даёт `refetch`, кнопка «Повторить поиск» просто
  запрашивает заново. Индикатор загрузки — `isFetching`, не `isLoading`
  (иначе ретрай не показывал бы pulse-анимацию повторно).
  `SEARCH_FAILED`-событие машины осталось объявленным, но стало
  недостижимым из обычного UI — ошибка обрабатывается локально в панели, не
  переходом состояния. Не удаляли событие из машины ради согласованности с
  остальными явно смоделированными сценариями (и на случай будущего
  QA/тестового сценария).
- **Аватар — инициалы на круге `bg-primary`, не внешний сервис/фото** —
  согласовано с Eugene: не тянуть внешнюю сетевую зависимость помимо
  MapTiler ради плейсхолдера. `DriverInfo.avatarUrl` (было в старом типе)
  убрали как неиспользуемое поле при переносе типа в `entities/driver`.
- **`DriverCard` — персистентная карточка сверху карты** (не bottom sheet),
  показывается на `driverAssigned`/`enRoute`/`arrived`/`inRide`, пока эти
  состояния всё ещё листаются debug-панелью снизу (реальный тикающий
  трекинг — следующий пункт роадмапа, не в этом шаге) — карточка и
  debug-панель не конфликтуют по расположению (верх/низ экрана).
- Проверено в браузере (Playwright, 4 прогона): happy path — карточка
  появляется автоматически без лишнего клика, все 3 профиля из пула
  встречались, ноль консольных ошибок. Error-path (20% шанс) не выпал ни
  разу за 4 прогона — код симметричен уже проверенному
  `ClassPickerSheet`-паттерну (`isError`/`isLoading` от RTK Query), отдельно
  форсировать не стали.

## 2026-07-16 — Поездка в реальном времени: авто-переходы + цена, зафиксированная при заказе

`driverAssigned → enRoute → arrived → inRide → completed` перестал
листаться вручную через debug-панель — трекинг (`useDriverLocationSimulator`,
переименован в `useRideAutomation`) теперь сам двигает машину состояний.

- **Цена фиксируется в момент `CONFIRM_CLASS`, не пересчитывается при
  `RIDE_COMPLETED`.** Раньше `RIDE_COMPLETED` нёс `fare` из
  захардкоженного `DEMO_FARE` в debug-панели. Теперь `ClassPickerSheet` уже
  знает точную цену выбранного класса в момент клика (`quotes.find(q =>
  q.classId === selectedClassId)`) и кладёт её в `context.fare` сразу же —
  `RIDE_COMPLETED` стал событием без payload. Так и в настоящих
  такси-приложениях: цена фиксируется при заказе, а не пересчитывается по
  приезду. Заодно избегает гонки — не пришлось бы гадать, готова ли цена к
  моменту, когда доедет анимация.
- **`useAnimatedPosition` получил `onComplete`** — коллбэк на кадре, где
  прогресс впервые доходит до 1. Хранится в `useRef`, синхронизируемом
  отдельным `useEffect` без deps («latest ref» паттерн) — если бы
  `onComplete` попал в зависимости самого rAF-эффекта, каждый ре-рендер
  перезапускал бы анимацию заново (та же ловушка, что раньше была с
  нестабильной ссылкой на `polyline`).
- **`useDriverLocationSimulator` → `useRideAutomation`** — переименован, а
  не расширен по месту под старым именем: хук и раньше слал
  `DRIVER_LOCATION_UPDATE` в машину, теперь ещё и таймер
  `driverAssigned → enRoute` (2с) и завершение каждой ноги →
  `DRIVER_ARRIVED`/`RIDE_COMPLETED`. Имя `...LocationSimulator` больше не
  описывало бы, чем хук на самом деле занят.
  `arrived → inRide` **остался кнопкой** «Начать поездку» в `DriverCard` —
  осознанное решение, не таймер: это момент, где пассажир садится в
  машину, реальное действие пользователя, а не то, что решает трекинг.
- **`DriverCard` — единственное место со статус-текстом и контекстным
  действием**, не отдельный оверлей рядом. Debug-панель полностью потеряла
  ветки `driverAssigned`/`enRoute`/`arrived`/`inRide` (тот же паттерн
  расширения раннего `return null`, что уже применялся трижды раньше).
- Заодно поправили кнопку «Оплатить» в debug-панели — брала сумму из
  своего собственного `DEMO_PAYMENT` (350₽) независимо от реальной цены;
  теперь читает `context.fare?.amount`, иначе рядом с настоящей ценой
  осталась бы явно неверная цифра.
- Проверено в браузере (Playwright): полный автоматический цикл от
  подтверждения класса до `completed` без единого лишнего клика (кроме
  осознанного «Начать поездку»), статус-текст меняется на каждом шаге
  ровно по расписанию (~2с/~6с/~6с), карточка водителя корректно исчезает
  на `completed`, ноль консольных ошибок.

## 2026-07-16 — Оплата / оценка поездки: реальный чек, без правок машины

`completed`/`done` получили настоящий UI (`RideCompletionSheet`,
`RideDoneCard`) вместо debug-кнопок с захардкоженным методом оплаты
(`'card'`) и рейтингом (`DEMO_RATING`, всегда 5 звёзд).

- **Ни одной правки в `machine.ts`.** `payment`/`rating` — уже независимые
  параллельные регионы, `SUBMIT_PAYMENT`/`SUBMIT_RATING`/`RESET` уже
  покрывали сценарий. Вся фича — UI поверх существующей машины, признак,
  что модель состояния была спроектирована верно ещё на этапе
  `machine.ts` (см. запись про параллельное состояние `completed`).
- **Партиальный матч по параллельным регионам** — `snapshot.matches({
  completed: { payment: 'pending' } })` вместо ручного каста
  `snapshot.value as {...}`, которым раньше пользовалась debug-панель.
  Идиоматичный способ читать вложенный parallel-state в XState v5, каст
  ушёл вместе с блоком, который его использовал.
- **`shared/lib/` — новая директория**, `formatCurrency.ts`
  (`formatCurrencyRUB`) вынесен из `ClassPickerSheet` при появлении
  второго потребителя (чек в `RideCompletionSheet`) — тот случай, когда
  копипаста одного и того же `Intl.NumberFormat` в третий раз уже не
  оправдана. `src/lib/utils.ts` (`cn`) — отдельно, это shadcn-CLI
  артефакт, не наш слой `shared/`.
- **Оплата и рейтинг — независимые блоки на одном экране**, не
  последовательные шаги — отражает то, как машина их и моделирует
  (параллельные регионы, `onDone` ждёт оба). Пользователь может оплатить и
  оценить в любом порядке.
- Debug-панель после этой фичи обслуживает только `idle` — единственный
  оставшийся пробел на пути к прод-демо (кнопка «Начать заказ» нигде,
  кроме dev-панели, недоступна). Зафиксировано в `architecture.md`, не
  чинится здесь — отдельный вопрос до финального пункта роадмапа
  «как Миша будет смотреть демо».
- Проверено в браузере (Playwright): чек показывает водителя/расстояние/
  цену, переключение на «Наличные» + «Оплатить» → подтверждение оплаты, 3
  звезды + «Оценить» → подтверждение рейтинга, автопереход в `done`
  (parallel `onDone`), «Заказать снова» возвращает в `idle`, ноль
  консольных ошибок.

## 2026-07-16 — Навигация: лёгкий контекст вместо роутера + выход debug-панели на пенсию

Профиль — первый второй экран, впервые понадобилась навигация. Взяли не
`react-router`, а маленький app-контекст (`app/navigationContext.ts` +
`NavigationProvider.tsx`, состояние `screen: 'order' | 'profile'`).

- **Почему не роутер:** сердце приложения — XState-флоу заказа, а не набор
  страниц; активный заказ нельзя прерывать произвольной URL-навигацией.
  URL-роутинг/deep-links для витрины без бэкенда ценности не добавляют, а
  дают лишний слой. Дальше по роадмапу только «История поездок» — третий
  экран впишется тем же `Screen`-объединением. Если позже понадобятся
  настоящие URL (например, для PWA-share), заменить контекст на роутер —
  локальная замена, экраны уже развязаны.
- **`OrderFlowProvider` поднят из `OrderScreen` в `App`** — чтобы
  XState-актор жил над переключателем экранов и не сбрасывался при
  профиль→заказ. Аватар и так виден только на `idle`, но держать актор
  живым правильнее на будущее.
- **Навигацию потребляют экраны, не фичи.** `IdleOverlay` (вход в заказ +
  аватар в профиль) — в `screens/order/`, а не в `features/order-flow/`:
  фича не должна знать про app-навигацию. Контекст разбит на `.ts`
  (хук+контекст) и `.tsx` (провайдер) — иначе `react(only-export-components)`
  дал бы warning (как в button.tsx), а мы держим lint чистым.
- **Debug-панель (`OrderFlowDebugPanel`) удалена.** Она была
  dev-only-скаффолдом для прогона состояний; после того как `idle` получил
  реальный `IdleOverlay` («Начать заказ»), не осталось ни одного состояния
  без настоящего UI. Заодно закрыт давний прод-пробел — раньше войти в
  заказ можно было только через dev-панель. Скаффолд-этап окончен.
- **`InitialsAvatar` вынесен в `shared/ui/`** — третий потребитель
  инициала-на-круге (карточка водителя, аватар на idle, шапка профиля),
  та же логика «третья копипаста не оправдана», что с `formatCurrency`.
- **Аватар на idle прогревает кэш профиля** (`useGetUserProfileQuery` в
  `IdleOverlay`) — профиль открывается мгновенно; пока грузится — иконка
  `User` вместо инициала (честный placeholder, без мигания пустым кругом).
- Проверено в браузере (Playwright): idle показывает аватар + «Начать
  заказ», переход в профиль (имя/телефон/рейтинг/оплата через MSW), back в
  idle, полный флоу заказа по-прежнему работает, debug-панель нигде не
  рендерится, ноль консольных ошибок.

## 2026-07-20 — Реальная геолокация: модель Яндекса «Я»≠A + фикс невидимой A

Достали из «Открытое». Первый браузерный device-API в проекте. Плюс
попутно вскрылся реальный баг (Eugene заметил по скрину Яндекса).

- **Отдельный шаг `selectingPickup`** перед `selectingDestination` (было:
  один drag ставил Б, A — фиксированная демо). Теперь `idle → selectingPickup
  → selectingDestination → …`: сначала уточняешь точку подачи A, потом Б —
  как в Яндексе. `context.userLocation` («Я», реальный GPS) — **отдельно**
  от `pickup` (A): «Я» стоит на реальной позиции, A можно двигать. По
  запросу Eugene — полная модель, не упрощение «A = твоя позиция».
- **`shared/lib/useCurrentPosition`** — Geolocation API один раз, `{status,
  coords}`. Требует secure context (https/localhost) — на dev/preview
  работает, на хостинге нужен https (⚠️ учесть на демо-шаге). При
  отказе/таймауте — `status: 'error'`, fallback на `DEMO_PICKUP` + тихая
  заметка. Ждём сетления перед постановкой A (по решению Eugene) — без
  гонки «демо-точка мелькнула вместо реальной».
- **`jumpTo`, не `flyTo`.** Нашли в браузер-проверке: кросс-страничный
  `flyTo` (Москва→СПб) анимируется несколько секунд, и быстрый «Подтвердить
  подачу» читал `map.getCenter()` mid-flight → точка A вставала не туда.
  `jumpTo` снепает мгновенно — и корректнее, и приятнее («нашли вас — вот
  вы тут»). Пример, почему браузер-проверка обязательна: на глаз/типах
  этого не видно.
- **Фикс «метку A не видно» — центр-пин сделали изумрудным**
  (`fill-primary` вместо `fill-foreground`). Причина бага: чёрная метка A
  (`var(--foreground)`) рисовалась ровно под чёрным центр-пином на одной
  точке — камуфляж. Метку A оставили чёрной (различима с водителем-изумрудом
  и Б-красным на этапе поездки), а перекрасили инструмент выбора (центр-пин).
- **`MapCanvas` — `variant: 'dot'`**: кастомный элемент `.location-dot`
  (`index.css`, изумруд + белое кольцо + pulse, через токены) для «Вы
  здесь», в отличие от teardrop-pin'ов A/Б/водителя.
- Проверено (Playwright, `grantPermissions(['geolocation'])` +
  `setGeolocation`): success — «Определяем…» → снеп к реальной точке, «Вы
  здесь» dot + изумрудный центр-пин, подтверждение подачи → `selectingDestination`
  с **видимой чёрной меткой A** (отдельно от изумрудного центр-пина) + «Назад»
  → полный цикл до класса; fallback (без permission) — заметка «Не удалось
  определить», флоу проходит на `DEMO_PICKUP`. Ноль консольных ошибок.

## 2026-07-20 — Геолокация сразу при входе, авто-подтверждение точки A (полная модель Яндекса)

Референс — Яндекс.Такси: геопозиция определяется сразу при открытии
приложения, точка A выставляется автоматически, отдельного шага
«подтвердите точку подачи» нет. Раньше запрос геолокации стартовал только
после «Начать заказ» (`selectingPickup`), плюс требовалось перетащить
карту и нажать кнопку подтверждения.

- **`SelectingPickupControls.tsx` → `PickupResolver.tsx`**, монтируется в
  `OrderScreen` по условию **`idle` ИЛИ `selectingPickup`** (было только
  `selectingPickup`). Компонент теперь и резолвит геолокацию (эффект
  `SET_USER_LOCATION`+`SET_PICKUP`+`jumpTo`, без изменений в логике), и
  сразу шлёт `CONFIRM_PICKUP`, как только `pickup` известен — кнопка
  «Подтвердить точку подачи» и текст-подсказка про drag убраны целиком. В
  типичном случае (геолокация успела резолвиться ещё на `idle`) пользователь
  вообще не видит `selectingPickup` — переход мгновенный.
- **Почему монтирование именно по `idle || selectingPickup`, а не
  постоянно на `OrderScreen`:** `useCurrentPosition` — fetch-on-mount.
  Если бы компонент не размонтировался на время поездки
  (`selectingDestination → … → done`), второй заказ подряд после `RESET`
  остался бы без геопозиции — запрос физически не переспросился бы.
  Монтирование по union двух состояний даёт естественный
  unmount/remount на каждом новом цикле заказа, тот же паттерн, что уже
  использует `IdleOverlay`/`DriverCard`. Проверено Playwright-скриптом,
  гоняющим два полных цикла заказа подряд — геолокация резолвится оба раза.
- **`SET_USER_LOCATION`/`SET_PICKUP` подняты в top-level `on` машины**
  (были только в `selectingPickup.on`) — событие теперь безопасно слать и
  из `idle`. Идиоматично для XState v5: top-level `on` — дефолтный
  обработчик для всех состояний, состояние может переопределить.
- **Убрана кнопка «Назад» (`BACK_TO_PICKUP`) на `selectingDestination`.**
  Прямое следствие авто-подтверждения: раз `selectingPickup` больше не
  ждёт ручного действия, клик «Назад» уводил в `selectingPickup`, которое
  тут же само отправляло `CONFIRM_PICKUP` обратно — кнопка превращалась в
  no-op (визуально «моргает» на то же место). Нашли Playwright-проверкой,
  убрали кнопку и событие `BACK_TO_PICKUP` целиком (из `machine.ts` и
  `types.ts`) как мёртвый код, а не оставили тихо сломанным.
- **Сознательно не в скоупе:** drag-to-refine точки A (раньше можно было
  подвинуть карту перед подтверждением — при авто-подтверждении для этого
  физически нет времени/шага). Если понадобится ручное уточнение A — это
  отдельная фича (например, тап по плашке «Точка подачи», как на скрине
  Яндекса), не восстановление старого шага.
- Проверено (Playwright): success-путь (permission+coords, «Я»-dot виден
  уже на `idle` до клика, клик «Начать заказ» ведёт сразу на
  `selectingDestination`), fallback-путь (без permission, тот же
  авто-переход на `DEMO_PICKUP`), и повторный заказ (два полных цикла
  `idle → … → done → RESET → idle` подряд, геолокация резолвится оба
  раза). Ноль консольных ошибок на всех прогонах.

## 2026-07-20 — Маршрут по дорогам через OSRM (road-snapping), а не по прямой

Референс — Яндекс.Такси: машина едет по дорогам. И линия маршрута, и
анимация маркера водителя были прямой A→Б (скаффолд-упрощение). Теперь —
реальная road-геометрия.

- **Источник — OSRM demo-сервер** (`router.project-osrm.org`), бесплатно,
  без ключа. Рассматривали MapTiler Directions (единый вендор с тайлами),
  но это отдельный beta-продукт («Routing & logistics APIs», join-the-beta),
  недоступен под текущим ключом — проверено по докам MapTiler. OSRM demo —
  стандартный выбор для прототипов; fair-use лимиты, без SLA, но нам этого
  достаточно (витрина).
- **`routingApi` — RTK Query с реальным внешним `baseUrl`, вне `entities/`
  и вне MSW.** Лежит в `shared/map/` (инфраструктура карты, как тайлы), не
  в `entities/*` — это не доменная сущность и не мокнутый эндпоинт (нет
  `mocks.ts`, не `/api`). RTK Query (а не голый fetch) — ради кеша по
  аргументам (не перезапрашивать на ре-рендере) и **дедупа**: линия в
  `OrderScreen` и inRide-нога в `useRideAutomation` шлют один и тот же
  `pickup→destination` → один сетевой запрос. Плюс соблюдает правило «нет
  fetch в компонентах». MSW на `onUnhandledRequest: 'bypass'` — вызов к
  другому origin проходит насквозь и в dev, и в prod, моки не мешают.
- **Fallback на прямую линию** (`roadOrStraight()`): пока запрос pending
  или если OSRM недоступен/лимит — рисуем/анимируем прямую A→Б, флоу не
  ломается. Демо не должно падать из-за флаки внешнего сервиса без SLA.
  Проверено Playwright'ом с заблокированным OSRM — полный цикл до `done`
  без ошибок.
- **Запрос гейтится на подтверждённые точки, не на drag.** `context.destination`
  ставится только на CONFIRM (не на каждый кадр перетаскивания), плюс оба
  запроса включаются с `selectingClass` (когда A и Б уже известны) —
  road-геометрия успевает закешироваться до старта своей ноги, анимация не
  рестартует на смене полилинии mid-leg. Проверено: 0 запросов к OSRM на
  перетаскивании, 2 (дедупнутых) после подтверждения.
- **Частичный пересмотр скаффолд-ADR «фейковая интерполяция маршрута
  вместо routing API»** (`_archive/decisions-scaffold.md`): геометрию
  теперь берём из настоящего routing-сервиса. Но **тайминг/скорость
  по-прежнему фейковые** (`LEG_DURATION_MS` фиксированный на ногу,
  rAF-интерполяция `useAnimatedPosition`) — это витрина, не настоящий
  трекинг; масштабировать длительность по реальной длине маршрута
  сознательно не стали.
- **Линия — сплошная тёмная** (`var(--foreground)`, убрали `line-dasharray`,
  `line-width` 3→4): читается как настоящий маршрут навигации и не сливается
  с изумрудным маркером такси.
- Проверено (Playwright, реальная сеть): линия A→Б изгибается по улицам
  (не прямая), обе ноги (`enRoute`/`inRide`) маркер едет по дорогам,
  fallback при заблокированном OSRM, отсутствие флуда запросов. Скриншоты
  подтверждают road-геометрию. Ноль консольных ошибок.

      `import.meta.env.DEV` — тестам он нужен для проверки геометрии
      маршрута и камеры.
    - **Внешние API мокаются через MSW, не `page.route()`.** Первая
      попытка — мокать OSRM/MapTiler через `page.route()` в тестовом
      файле — не сработала: запросы были видны в `page.on('request')`,
      но обработчик `route()` ни разу не сработал. Причина — активный
      Service Worker (MSW): fetch, который SW пропускает дальше в сеть
      (`onUnhandledRequest: 'bypass'`), выполняется в собственном
      контексте SW, отдельном CDP-таргете от страницы — `page.route()`
      этого не видит (подтверждено экспериментом: добавил
      `console.log` в обработчик route — ни разу не вызвался, при этом
      сами запросы шли и долетали до реального OSRM/MapTiler). Раз MSW
      и так уже единственный слой перехвата в приложении — мокаем через
      него же: `src/shared/mocks/e2e-handlers.ts` с хендлерами для OSRM/
      MapTiler (geocoding + style), подключаются в `browser.ts` только
      когда `import.meta.env.VITE_E2E` — переменную выставляет
      исключительно `webServer.env` в `playwright.config.ts`; обычный
      `npm run dev` и прод (Vercel) её не видят, там OSRM/MapTiler
      остаются настоящими сервисами, как и задумано изначально. Мок-стиль
      карты — `{version:8, sources:{}, layers:[]}` (валидный, карта
      грузится мгновенно офлайн; MapLibre не запрашивает тайлы для
      несуществующих источников — отдельно мокать тайлы не пришлось).
    - **Собственные `/api/*` не мокаются повторно** — тесты используют
      тот же MSW-бэкенд, что и обычная разработка. `driver-search` имеет
      встроенную 20%-ю случайность отказа (`entities/driver/mocks.ts`) —
      обрабатывается ретраем в самом тесте (клик «Повторить поиск» в
      цикле до появления `DriverCard`), не отдельным мокoм — заодно
      покрывает retry-UI.
    - **`page.clock` для перемотки времени поездки.** Полный флоу
      завязан на реальные задержки: `driverAssigned→enRoute` (2с,
      `setTimeout` в `useRideAutomation.ts`) и две 6-секундные rAF-
      анимированные ноги (`useAnimatedPosition.ts`, время читается через
      `performance.now()`). Без перемотки — 15+ реальных секунд на
      каждый прогон, неприемлемо для гейта-на-коммит.
      `page.clock.install()` + `fastForward()` эмпирически подтверждён
      консистентно двигающим и `setTimeout`, и rAF/`performance.now()`
      вместе (мини-эксперимент до написания финального теста: статус
      карточки водителя корректно переходил «Едет к вам» →
      «Ждёт у подъезда» после одного `fastForward(6200)`). MSW-шные
      искусственные задержки (`delay()` внутри Service Worker) фейком не
      затрагиваются — не тот JS-контекст — остаются короткими честными
      ожиданиями (~0.5–2.5с), это и ограничивает нижнюю границу времени
      прогона (не 15с, но и не мгновенно).
  - **Санити-проверка**: временно сломал `roadOrStraight()` (вернуть
    всегда прямую линию) — тест `pickup-destination.spec.ts` покраснел
    ровно на той самой проверке, что и должен (`coords.length > 2`);
    откатил. Подтверждает, что набор реально ловит регресс, а не просто
    зелёный по случайности.
  - Набор: `e2e/smoke.spec.ts`, `e2e/pickup-destination.spec.ts`,
    `e2e/full-ride.spec.ts` (полный happy-path A→оплата/рейтинг→RESET).
    Весь прогон — секунды (~10с локально), не десятки.
  - **Отложенный пункт (явная просьба Eugene не терять): Playwright
    MCP.** Обсуждали как альтернативу/дополнение — таблица
    плюсов/минусов в переписке 2026-07-25. Решили: НЕ заменяет ни
    регресс-сеть (эта запись), ни разовые Node-скрипты для глубокой
    отладки (кастомные ассерты, `page.evaluate` в живое состояние

    отдельной задачей, когда понадобится ускорить именно ad-hoc
    тыканье — см. `docs/roadmap.md`.
